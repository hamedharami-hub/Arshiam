# الگوی آموزشی چندکارتی — قرارداد طراحی نسخهٔ ۱

خواستهٔ مستقیم کاربر: هر درس از کارت‌های مجزا و نام‌دار تشکیل شود؛ کارت‌ها دستهٔ مشخص داشته باشند و در گروه‌های افقی و بخش‌های عمودی ترکیب شوند. این الگو بعداً برای کتاب‌ها و حوزه‌های آموزشی دیگر نیز استفاده شود.

این سند مکمل پلن جامع نسخهٔ ۳ است. قرارداد طراحی و پیاده‌سازی است؛ پایهٔ نمایش اجرا شده و وضعیت دقیق آن در انتهای سند آمده است.

## ساختار محتوا

```text
حوزه / کتاب
└── مجموعهٔ اصلی
    └── شاخه
        └── زیرشاخه‌های مورد نیاز
            └── درس
                ├── گروه کارت: شناخت موضوع
                │   ├── کارت نام‌دار: تعریف
                │   └── کارت نام‌دار: ویژگی‌ها
                ├── گروه کارت: کاربرد و تحلیل
                │   ├── کارت نام‌دار: کاربرد
                │   ├── کارت نام‌دار: مثال
                │   └── کارت نام‌دار: نکات مهم
                └── گروه کارت: تمرین و ادامه
                    ├── کارت نام‌دار: پرسش موجود
                    └── کارت نام‌دار: درس‌های مرتبط
```

تعداد زیرشاخه‌ها از داده تعیین شود؛ عمق ثابت یا تکرار اجباری گروه‌ها لازم نیست. breadcrumb کوتاه و درخت جمع‌شونده مسیر کامل را نشان دهند. «نوع کارت» و «پوشهٔ درس» دو مفهوم مستقل‌اند؛ مثلاً کارت عوارض در درس یک دارو قرار دارد، نه اینکه برای عوارض یک نسخهٔ تکراری از درس ساخته شود.

**کارت آموزشی** بخش دارای معنای مستقل از درس است. **کارت مرور** سؤال/پاسخ زمان‌بندی‌شده در Review است. رابطهٔ آن‌ها با شناسهٔ کارت آموزشی ثبت شود؛ ذخیره و پیشرفتشان جدا باشد.

## قرارداد هر کارت

هر کارت: شناسهٔ پایدار، عنوان مخصوص، دسته/نوع، محتوای کامل، ترتیب خواندن، گروه والد، زبان، مبدأ و منابع مرتبط. عنوان مشخص مانند «عوارض مهم»؛ عنوان‌های مبهم «بخش ۱» فقط fallback برای محتوای قدیمی باشند.

ساختار پیشنهادی داده:

```ts
type LessonCard = {
  id: string; lessonId: string; groupId: string;
  type: string; // definition, mechanism, indication, adverseEffects, example…
  title: { fa?: string; en?: string };
  body: { fa?: string; en?: string }; // محتوای معتبر با ساختار معنایی
  order: number;
  size: 'compact' | 'standard' | 'wide';
  sourceBlockIds: string[];
  referenceIds: string[];
};
type CardGroup = {
  id: string; lessonId: string;
  title: { fa?: string; en?: string };
  layout: 'grid' | 'sequence' | 'fullWidth';
  order: number; cardIds: string[];
};
```

شناسه از موقعیت آرایه یا عنوان ترجمه‌شده ساخته نشود. لینک `lesson/card`، annotation، فایل، کارت مرور و محل ادامه به همان شناسه وصل شوند. مدل فعلی document حفظ و نمای چندکارتی به‌صورت تدریجی به آن افزوده شود؛ مهاجرت همهٔ داده‌ها در یک تغییر بزرگ لازم نیست.

## ترکیب افقی و عمودی

هر گروه یک تیتر کوتاه دارد. کارت‌های کوتاه و هم‌سطح کنار هم؛ متن بلند، جدول و هشدار حساس تمام‌عرض؛ مراحل دارای ترتیب به صورت sequence. حداکثر سه ستون در فضای کافی، دو ستون در فضای متوسط و یک ستون برای کارت متنی بلند در موبایل. تعداد ستون بر اساس **عرض فضای درس** تعیین شود.

```text
عنوان درس + مسیر کوتاه + کنترل زبان

گروه شناخت
┌─────────────┬─────────────┬─────────────┐
│ تعریف       │ ویژگی‌ها    │ کاربرد      │
└─────────────┴─────────────┴─────────────┘

گروه نکات مهم
┌───────────────────────────────────────┐
│ هشدار / نکتهٔ اصلی — تمام‌عرض         │
└───────────────────────────────────────┘
┌───────────────────┬───────────────────┐
│ جزئیات اول        │ جزئیات دوم        │
└───────────────────┴───────────────────┘

گروه یادگیری
┌───────────────────┬───────────────────┐
│ مثال              │ تمرین موجود       │
└───────────────────┴───────────────────┘
```

- افقی‌بودن از grid و گروه‌بندی حاصل شود؛ صفحهٔ درس به چند ردیف carousel تبدیل نشود. کارت‌های خارج دید نباید تنها محل هشدار ضروری باشند.
- روی موبایل، کارت‌های کوتاه انتخاب مسیر/اصطلاح می‌توانند در یک ردیف افقی با نشانهٔ ادامه قرار گیرند؛ متن اصلی بدون اسکرول افقی خوانده شود.
- تب‌ها برای رفتن به **گروه‌ها**، مثلاً شناخت/کاربرد/تمرین/منابع؛ هر تب خودش چند کارت دارد. هر کارت کوچک یک تب جدا نشود.
- نمای «همهٔ کارت‌ها» برای مطالعهٔ پیوسته و جست‌وجو باقی باشد؛ کارت و بخش فعال در URL قابل ارجاع باشند.
- چینش masonry نامنظم پیشنهاد نمی‌شود؛ ترتیب دیداری و DOM باید با ترتیب خواندن، RTL و صفحه‌کلید یکسان بماند.

## شکل و اجزای کارت

سطح خنثی، border آرام، گوشه‌های یکسان و سایهٔ کم. آیکون کوچک اختیاری، عنوان ۱۵–۱۷ و متن حدود ۱۵–۱۶ پیکسل در اندازهٔ پیش‌فرض؛ تنظیم فونت حفظ شود. رنگ معنایی محدود برای هشدار/پاسخ/مثال؛ نوع کارت با متن هم روشن باشد.

سربرگ کارت: عنوان در اولویت، نوع در صورت ابهام، منوی فرعی. پایین کارت: منبع مرتبط و اقدامات اختیاری «یادداشت، پیوست، مرور»؛ این اقدامات دائماً فضای متن را اشغال نکنند. روی موبایل منوی واحد یا نوار انتخاب متن. حداقل یکی از عنوان گروه/نوع کارت برای معنا کافی است؛ برچسب تکراری در هر کارت نمایش داده نشود.

کارت بلند: پیش‌نمایش فقط با نشان واضح «ادامه» و امکان بازکردن کامل؛ هشدار، منع مصرف و شرایط ضروری بی‌خبر قطع نشوند. صفحهٔ کامل یا پنل برای محتوای بلند؛ زنجیرهٔ پاپ‌آپ داخل پاپ‌آپ کاهش یابد. ارتفاع یکسان اجباری برای همهٔ کارت‌ها یا فضای خالی عظیم زیر کارت کوتاه نباشد.

## نام‌گذاری و دسته‌بندی

رجیستری نوع کارت قابل توسعه باشد. نمونهٔ فارماسی: معرفی، نشانه‌ها، ارزیابی، کاربرد، مکانیسم، مقدار/روش مصرف، عوارض، منع مصرف، تداخل، مشاوره، نگهداری، مثال، سناریو، تمرین، منابع. نمونهٔ کتاب عمومی: تعریف، مفهوم، استدلال، مثال، نمودار، روش، تمرین و جمع‌بندی.

دستهٔ خالی ساخته نشود؛ برای هر درس فقط محتوای موجود نمایش داده شود. فیلدهای فنی مثل شناسه و نام کلاس رنگ به metadata منتقل شوند، ولی اطلاعات مبدأ و منابع قابل دسترسی بمانند. ترجمهٔ عنوان و متن به هم نگاشت داشته باشد؛ تغییر زبان نوع یا ترتیب کارت را تغییر ندهد.

## پیشرفت و اتصال

- آخرین درس، گروه، کارت و موقعیت خواندن قابل ادامه باشند؛ «بازشدن کارت» به‌تنهایی یادگیری یا تسلط نامیده نشود.
- پیشرفت خواندن و تمرین با تعریف روشن و رویداد واقعی؛ مقدار ساختگی و badge بدون داده نمایش داده نشود.
- annotation و عکس/فایل به کارت یا محدودهٔ متن آن وصل شوند؛ نمای کل درس یادداشت‌های همان کارت‌ها را جمع کند.
- تبدیل نکته به کارت Review، مبدأ دقیق و جلوگیری از تکرار داشته باشد؛ تأیید پیش از ساخت/بازنویسی گسترده.
- ارتباط درس با محصول/بیماری/مکانیسم/سناریو به کارت‌های مرتبط ختم شود؛ رفتن و برگشت متن و موقعیت را نگه دارد.

## انتقال محتوای موجود

برای هر سند، blockها و معنای موجود استخراج و به کارت‌ها نگاشت شوند. `<div>` شبیه تیتر یا `<dt>` شناخته‌شده می‌تواند با mapping بازبینی‌شده عنوان کارت شود؛ هر div یا فیلد JSON کارت مستقل نیست. منبع و متن کامل قبل/بعد قابل مقایسه باشند. نوع درس از metadata و mapping تعیین شود، نه فقط regex عنوان.

متن علمی، دوز، هشدار، قانون و پاسخ صحیح تغییر نکند. شناسه و پیشرفت موجود حفظ شوند؛ نسخهٔ ویرایش‌شدهٔ کاربر خودکار با seed جایگزین نشود. موارد مبهم برای بررسی جدا علامت بخورند. هر تبدیلی preview و مسیر بازگشت داشته باشد.

## پذیرش و اجرای اقتصادی

ابتدا شش درس نماینده، یکی از هر مجموعهٔ فارماسی، ساخته و بررسی شوند؛ سپس زیرنوع‌های متفاوت و بعد باقی درس‌ها. برای هر کارت: عنوان/نوع/گروه/مبدأ روشن؛ هیچ blockی گم نشده؛ لینک بخش، زبان، فایل، یادداشت و بازگشت صحیح. اندازهٔ کارت متناسب متن و عرض پنل باشد.

نمونهٔ اولیه در ۳۹۰/۸۵۳/۱۴۴۰، روشن/تیره/OLED و فارسی/انگلیسی بررسی شود؛ کنترل کوچک و طولانی، صفحه‌کلید نرم، focus و zoom هم پوشش داده شوند. استفاده از قالب مشترک هزینه را کم می‌کند، ولی بررسی اختلاف واقعی زیرنوع‌ها حذف نشود.

## وضعیت نخستین پیاده‌سازی

نمای کارت‌های گروه‌بندی‌شده و متن اصلی، عنوان استخراج‌شده از تیتر/فیلد، چیدمان وابسته به عرض پنل و مشخصات مبدأ جمع‌شونده در خوانندهٔ مشترک پیاده شده‌اند. این مرحله adapter نمایش است؛ schema کارت مستقل ابری، annotation کارت و ادامهٔ دقیق کارت هنوز اجرا نشده‌اند. شناسهٔ استخراج‌شده از عنوان در این مرحله برای نمای همان زبان است؛ قرارداد شناسهٔ دائمی چندزبانه در مرحلهٔ schema باید تکمیل شود.
