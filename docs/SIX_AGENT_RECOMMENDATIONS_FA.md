# پیشنهادهای محصول و فنی پس از ممیزی

این سند از فهرست باگ‌ها جداست. موارد زیر پیشنهادهای مرحله‌ای‌اند؛ لازم نیست برای بستن باگ‌های این شاخه اعمال شوند. محتوای Knowledge عمداً بررسی نشده است.

## ۱. مدل برنامه‌ریزی کارها

- «چه روز/بازه‌ای برای انجام در نظر گرفته شده» را از «ساعت دقیق شروع» جدا نگه دارید. تاریخ یا افق برنامه‌ریزی برای اولویت و نمایش در Today کافی است؛ ساعت دقیق فقط وقتی لازم است که کار واقعاً قرار ملاقات یا زمان ثابت داشته باشد.
- Today را به فهرست قابل‌اقدام تبدیل کنید: کارهای امروز و سپس کارهای عقب‌افتاده. کارهای انجام‌شده از عقب‌افتاده‌ها کنار گذاشته شوند. عقب‌افتادگی از تاریخ/بازهٔ برنامه و روز محلی کاربر محاسبه شود، نه با زمان دستگاهی که سرور را تغییر می‌دهد.
- برای کارهای بدون زمان مشخص، برچسب‌هایی مثل «امروز»، «فردا»، «این هفته» یا «بعداً» از اجبار به انتخاب ساعت دقیق مناسب‌ترند. این برچسب‌ها باید به تاریخ محلی تبدیل و در دادهٔ اصلی به‌شکل یکنواخت ذخیره شوند.
- موعد تحویل را فقط اگر محصول واقعاً رفتار جداگانه‌ای برای آن دارد نگه دارید؛ نباید با برنامهٔ انجام یا زمان شروع یکی شود. اگر چنین تمایزی در UI ارزش روشنی ندارد، یک فیلد و یک منبع حقیقت داشته باشید.
- جابه‌جایی خودکار کارهای عقب‌افتاده به امروز را پیش‌فرض نکنید؛ این کار می‌تواند برنامهٔ کاربر را بی‌صدا تغییر دهد. در صورت نیاز، پیشنهاد انتقال را به‌عنوان اقدام صریح ارائه کنید.
- تکرار را از نمونهٔ جاری جدا کنید: والد تکرار، رخداد جاری و زیرکارهای آن باید مرز روشن داشته باشند. ساخت رخداد و به‌روزرسانی وابستگان را اتمی کنید و از ساخت دوبارهٔ همان رخداد در retry جلوگیری کنید.

## ۲. همگام‌سازی و تعارض چنددستگاهی

- به‌جای `updated_at` ساخته‌شده روی کلاینت، revision یکنواخت و متعلق به سرور (مانند شمارنده یا شناسهٔ نسخه) اضافه کنید. مهرزمان دستگاه ممکن است عقب یا جلو باشد و مبنای امنی برای تشخیص نسخه نیست.
- هر تغییر آفلاین باید مالک حساب، revision پایه و نوع عملیات را نگه دارد. اگر سند سرور تغییر کرده یا حذف شده، دادهٔ محلی را بی‌صدا جایگزین نکنید؛ تعارض را نگه دارید و امکان دیدن/اعمال دوبارهٔ نسخهٔ کاربر را بدهید.
- برای تعارض، UI مشخصی بسازید: نمایش نسخهٔ فعلی و نسخهٔ آفلاین، انتخاب یکی یا کپی‌کردن محتوا. صفی که revision پایه ندارد باید به مسیر بازیابی/تعارض منتقل شود، نه اینکه خودکار بازپخش شود.
- پاک‌سازی خروج از حساب یا حذف حساب را با شناسهٔ همان UID محدود کنید. تنظیمات عمومی دستگاه و دادهٔ آفلاین حساب‌های دیگر نباید پاک شوند.

## ۳. API و امنیت

- قرارداد هر endpoint را با schema ورودی و allowlist فیلدهای قابل‌نوشتن تعریف کنید. تغییر OpenAPI باید همراه تغییر route و تست قرارداد باشد.
- grantهای توکن را به کمترین دسترسی لازم محدود کنید و ماتریس scope به endpoint را تست کنید. عدم دسترسی باید پیش از خواندن/نوشتن داده برگردد.
- idempotency پایدار را برای عملیات ساخت/پرداخت/اجرای بیرونی نگه دارید؛ کلید را به هویت و hash درخواست وصل کنید و پاسخ یک درخواست تکراری را فقط برای payload یکسان بازگردانید. عمر رکورد و پاک‌سازی آن باید مشخص باشد.
- هم‌زمانی را در تراکنش پایگاه‌داده حل کنید. بررسی مسبق خارج از تراکنش برای `external_ref` یا وضعیت task در رقابت دو درخواست کافی نیست.

## ۴. حذف حساب و نگهداری داده

- حذف حساب باید فهرست مالکیت داده را صریح داشته باشد: Auth، درخت Firestore، Storage، داده‌های سرویس قدیمی FastAPI/Mongo، توکن‌های OAuth و کش/صف آفلاین همین UID.
- احراز هویت تازه را در سرور بررسی کنید، مالک را فقط از token بگیرید و Auth را آخر حذف کنید تا در شکست میانی کاربر بتواند حذف را دوباره اجرا کند.
- برای استقرار لازم است `ARSH_API_BASE_URL` در Vercel به سرویس FastAPI تنظیم شود؛ build وب باید دوباره deploy شود. برای اپ native نیز `VITE_ACCOUNT_API_URL` باید URL امن endpoint حساب باشد. بدون این متغیرها حذف عمداً fail-closed خواهد بود.
- حذف چند سامانه‌ای تراکنش توزیع‌شده نیست. برای مقیاس بالاتر، درخواست حذف را به job پایدار با وضعیت مرحله‌ای، retry امن و گزارش نتیجه تبدیل کنید؛ سپس در UI وضعیت «در حال حذف/نیازمند retry» نشان دهید.
- پیش از انتشار، با Firebase Emulator و دیتاست آزمایشی این موارد را بررسی کنید: کاربر دیگر حذف نشود، شکست هر مرحله Auth را باقی بگذارد، اجرای دوباره موفق شود و هیچ فایل/توکن یتیمی نماند.

## ۵. سلامت، Pharmacy و Pomodoro

- دادهٔ Pharmacy و جلسهٔ Pomodoro باید از ابتدا با UID کلید بخورد و پس از تغییر حساب پاسخ‌های دیررس دور ریخته شوند.
- آمار روزانهٔ جلسه را با روز پایان جلسه و منطقهٔ زمانی کاربر گروه‌بندی کنید؛ زمان شروع و مدت واقعی را نیز جدا نگه دارید.
- برای دادهٔ سلامت، cache محلی را از منبع سرور متمایز کنید و زمان آخرین همگام‌سازی/وضعیت خطا را نشان دهید تا کاربر snapshot کهنه را دادهٔ تازه فرض نکند.

## ۶. کیفیت و انتشار

- در CI، typecheck، تست کامل frontend، تست API و build را به‌عنوان gate اجرا کنید؛ تمرکز روی تست‌های کوچک به‌تنهایی مشکلات تعامل بین ماژول‌ها را نمی‌گیرد.
- برای سناریوهای حساس، تست یکپارچهٔ emulator اضافه کنید: دو دستگاه و دو UID، ویرایش آفلاین در برابر ویرایش ابری، تغییر حساب هنگام fetch، حذف حساب با شکست میانی و retry.
- یک smoke test مرورگری برای مسیرهای اصلی Tasks/Today/Calendar، تنظیمات، Pharmacy و Pomodoro در اندازهٔ موبایل و دسکتاپ اجرا کنید. Knowledge در دامنهٔ این ممیزی و پیشنهادهای اجرایی آن قرار نگرفته است.
- بعد از deploy، خطاهای conflict queue، حذف ناقص حساب، نرخ خطای API و شکست همگام‌سازی را با شناسهٔ درخواست و بدون ثبت محتوای خصوصی پایش کنید.

## اولویت پیشنهادی

۱. اعمال متغیرهای محیطی و استقرار هماهنگ endpoint حذف حساب با FastAPI؛ اجرای تست end-to-end حذف.
۲. نمایش/بازیابی تعارض صف آفلاین تا دادهٔ fail-closed برای کاربر قابل‌حل باشد.
۳. مهاجرت از timestamp کلاینت به revision سرور در نوشتن مستقیم و replay صف.
۴. افزودن تست‌های emulator و CI کامل برای جلوگیری از برگشت باگ‌های حساب، برنامه‌ریزی و sync.
۵. بازبینی مدل Today و برچسب‌های برنامه‌ریزی با دادهٔ واقعی استفاده، بدون افزودن زمان دقیق اجباری.
