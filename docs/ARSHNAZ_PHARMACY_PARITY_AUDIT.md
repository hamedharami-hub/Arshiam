## شواهد اعتبارسنجی

- آخرین اجرای `npm run build` موفق شد و typecheck داخل build نیز موفق بود؛ Vite هشدار chunkهای بزرگ و importهای هم‌زمان static/dynamic را داد.
- حذف اولیهٔ `firebase-admin` اشتباه بود: کد API به آن وابسته است و یک suite تست resolve نمی‌شد؛ وابستگی به manifest و lockfile برگردانده شد. نصب پاک با `npm ci --dry-run` و suite مربوط به API بعد از اصلاح موفق شدند.
- بررسی ایستای seed: صفر شناسهٔ تکراری، صفر پیوند شکسته و صفر سند بدون `source_url`.
- پس از اصلاح وابستگی، اجرای کامل Vitest موفق بود: ۸۳ فایل تست، ۴۵۸ تست.
- `npm run lint` موفق شد (۰ خطا، ۶۰ هشدار lint موجود در پروژه)؛ `npm run build` و typecheck نیز موفق شدند. اجرای build هنوز هشدارهای chunkهای بزرگ و importهای هم‌زمان static/dynamic دارد.
- `npm audit --omit=dev` اکنون ۸ آسیب‌پذیری Moderate در زنجیرهٔ `firebase-admin`/`uuid` نشان می‌دهد؛ رفع خودکار پیشنهادی به ارتقای breaking به `firebase-admin@14.5.0` نیاز دارد و در این اصلاح انجام نشد. audit کامل ۱۴ مورد (۱۳ Moderate، ۱ High) نشان می‌دهد؛ High در toolchain Vite است.
- `git diff --check` موفق بود؛ فقط هشدارهای line-ending ویندوز گزارش شد.
- chunk دادهٔ Pharmacy همچنان حدود ۳٫۶ MB پیش از فشرده‌سازی (حدود ۴۱۴ KB gzip) است، اما اکنون هنگام نیاز بارگیری می‌شود و در precache نیست. حجم precache با ۱۵۷ فایل حدود ۵٫۹ MB است (کاهش حدود ۴٫۵ MB). چند هشدار قدیمی Vite دربارهٔ importهای هم‌زمان static/dynamic نیز باقی است.
- `npm audit` کامل هنوز ۷ مورد در ابزارهای توسعه گزارش می‌کند: ۶ Moderate و ۱ High. مورد High به Vite و رفع پیشنهادی آن ارتقای major به Vite 8 است؛ این ارتقا در این مرحله برای جلوگیری از مهاجرت پرریسک toolchain انجام نشد. این‌ها در گزارش production-only audit دیده نمی‌شوند.

## موارد باز و مهم

1. کد ممیزی‌شده روی `main` و Vercel production منتشر شده است، اما Firestore زنده همچنان محتوای قدیمی CYP1A2 را نشان می‌دهد و خود صفحه هشدار می‌دهد ترجمهٔ فارسیِ متن ناقص است. انتشار کد به‌تنهایی دادهٔ حساب را وارد یا بازنویسی نمی‌کند.
2. سندهای Pharmacy فعلاً عمدتاً محتوای دانشی/ایستا هستند. تجربه‌های تعاملی Pharmacy—مصاحبه و triage OTC، جست‌وجوی ساختاریافتهٔ قفسهٔ دارو و شبیه‌سازی گردش کار FRED—هنوز به‌صورت workflowهای واقعی در ARSHNAZ پیاده‌سازی نشده‌اند.
3. ثبت لینک به فایل کد، منشأ داده را قابل ردیابی می‌کند اما جایگزین منبع اولیهٔ بالینی نیست. در schemaهای دادهٔ Pharmacy فیلدهای ساختاریافتهٔ `sourceUrl`، `reviewedAt`، `reviewBy`، `accessedAt` و `jurisdiction` پیدا نشدند؛ `ClinicalRelation.source/reason` توضیح منشأ/منطق داخلی رابطه است، نه citation بالینی. هر ادعای درمانی/دوز/تداخل/قانون باید به منبع جاری استرالیا، حوزهٔ قضایی، تاریخ بررسی و بازبین بالینی متصل شود. دادهٔ Pharmacy بدون این فرایند نباید «تأیید بالینی» تلقی شود.
4. گراف روابط نوع‌دار Pharmacy به‌صورت دادهٔ ساختاریافته منتقل، روی `main` منتشر و در شبکهٔ روابط قابل نمایش شده است؛ با این حال هیچ داده‌ای به Firestore زنده نوشته نشده و نمایش رکوردهای seed نیازمند import جداگانه و صریح است.
5. نتیجهٔ audit کامل وابستگی‌ها باید پیش از اعلام «آمادهٔ استفادهٔ نهایی» دوباره بررسی شود؛ major upgrade ابزار ساخت یک کار جدا و نیازمند اعتبارسنجی است.
6. ریسک بازگشت cache قدیمی اصلاح شد: پس از دریافت موفق remote، همان پاسخ مبناست و فقط mutationهای pending همان حساب و collection روی آن replay می‌شوند. این قاعده برای پوشه‌ها، اسناد، کارت‌های Leitner و پیوندهای تسک-دانش اعمال شده و تست رگرسیون cache-only deletion، insert/update/delete آفلاین و جداسازی حساب دارد.
7. جست‌وجوی نقشهٔ ذهنی اکنون نام پوشه، عنوان فارسی/انگلیسی سند، متن، tag، سؤال/پاسخ/clue کارت و تفاوت نویسه‌های عربی/فارسی را پوشش می‌دهد؛ تمام والدهای چندسطحی و سند والد کارت برای نمایان‌شدن نتیجه باز می‌شوند و این مسیر تست رگرسیون مستقل دارد.

## گام‌های بعدی پیشنهادی

1. بررسی بصری نسخهٔ محلی و آزمون عملی در browser؛ تست‌های UI صفحه محدودند و سناریوهای کامل reader، منوها و تعامل‌های واقعی هنوز آزمون خودکار ندارند.
2. پس از تأیید صریح برای محیط زنده، اجرای importer امن روی حساب Firestore هدف؛ ابتدا فقط شمارش missing/upgradeable نمایش داده شود و نتیجهٔ server-side تأیید گردد. محتوای ویرایش‌شده و کارت‌های موجود نباید overwrite شوند.
3. پیش از import زنده، پیش‌نمایش شمارش missing/upgradeable و تأیید عدم overwrite محتوای شخصی؛ انتشار وب کد طبق دستور حامد از شاخهٔ `main` انجام می‌شود.
4. توسعهٔ parity به‌ترتیب: کاتالوگ محصولات و فیلتر ساختاریافته؛ ابزارهای آموزشی OTC با مرز روشن عدم‌تشخیص؛ سپس شبیه‌ساز dispensing آموزشی. هر محتوای بالینی/حقوقی قبل از استفادهٔ عملی نیازمند source review و بازبین واجد صلاحیت است.

نسخهٔ اندروید عمداً ساخته نشده است.

## برنامهٔ ادامهٔ ممیزی و همسان‌سازی (درخواست ۲۵ سپتامبر)

این موارد پس از ثبت اصلاح فعلی در GitHub به ترتیب بررسی و اجرا می‌شوند. وضعیت «نیازمند آزمون» به معنی تأیید عملکرد نیست. دادهٔ زندهٔ Firestore و نسخهٔ اندروید در این برنامه تغییر نمی‌کنند مگر با تصمیم جداگانهٔ حامد.

1. **خواندن و ناوبری دانش:** نمایش متن فارسی/انگلیسی، لینک‌های درون متن و «مرتبط»، رفتن به دارو/بیماری هدف، بازگشت مرورگر و دکمهٔ بازگشت به سند قبلی، حفظ حالت و جایگاه خواندن؛ آزمون روی موبایل و نمایشگر بزرگ. باگ مشاهده‌شده: کلیک سند مرتبط، URL را عوض نمی‌کرد و Back به سند قبلی برنمی‌گشت. اصلاح URL و تست رگرسیون در این دور آماده شده و پس از انتشار باید زنده نیز آزموده شود.
2. **پرسش و Leitner:** مسیر «انتخاب متن یا checkpoint → تولید سؤال با AI/دستی → پیش‌نمایش قابل‌ویرایش → ذخیرهٔ پایدار کارت → مرور → بازگشت به منبع» با حالت‌های شکست، سؤال تکراری و تولید بی‌ربط آزموده شود. تنظیمات فاصلهٔ مرور، امتیازدهی، موعد، دسته‌بندی و نمای مرور با Pharmacy مقایسه شود؛ هر حالت موجود در Pharmacy که ارزش آموزشی دارد با معیار پذیرش مشخص منتقل شود. تولید AI بدون منبع‌سنجی به معنی درستی علمی نیست.
3. **نقشهٔ ذهنی:** حالت‌های نمایش و مطالعهٔ شاخه‌ها، فیلترها، بازکردن مسیر والد، جابه‌جایی سند/کارت و حفظ وضعیت با Pharmacy مقایسه و نواقص عملکردی جداگانه ثبت شود.
4. **زیر‌دسته‌های بیماری و دارو:** ساختار دسته‌بندی Pharmacy و نیازهای جست‌وجوی ARSHNAZ تطبیق داده شود؛ دسته‌های بیشتر تنها با شناسهٔ پایدار، رابطهٔ والد/فرزند روشن، بدون جابه‌جایی یا overwrite محتوای شخصی و با مهاجرت قابل‌آزمون اضافه شوند. متن درمانی تازه بدون منبع بالینی معتبر ساخته نشود.
5. **آموزش تعاملی مستقل:** یک ورودی و صفحهٔ مجزا برای تجربه‌های تعاملی Pharmacy طراحی شود. منبع مقایسه شامل `OtcTriageModule`، `DiseaseTriagePanel`، سناریوها/گام‌های triage و شبیه‌ساز `FredDispenseModule` است. جریان سناریو، انتخاب پاسخ، بازخورد، هشدارهای red flag و امکان بازشروع باید واقعاً تعاملی بماند، نه اینکه صرفاً متن ثابت منتقل شود. برای این بخش کپی متن یا انتقال به Leitner لازم نیست. تا بررسی علمی و حقوقی، برچسب «آموزشی، نه توصیهٔ درمانی یا مجوز عرضه» حفظ شود.
6. **اعتبار علمی و پذیرش نهایی:** هر ادعای حساس دارویی/دوز/تداخل/قانون با منبع معتبر، تاریخ، حوزهٔ قضایی و بازبین واجدصلاحیت بررسی شود. برای هر مرحله تست واحد/تعامل، تست ذخیره و بازگشت، typecheck، build و آزمون بصری production انجام شود. ابتدا وب؛ APK طبق درخواست فعلی ساخته نشود.
