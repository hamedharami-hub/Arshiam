## ترتیب و معیار عبور

۱. یافته فقط با سناریوی مشخص، مسیر کد و اثر روی کاربر وارد فهرست می‌شود. حدس‌های بدون شاهد، پیشنهاد هستند. شدت P0 برای از دست‌رفتن/افشای داده یا ادعای نادرستِ حذف؛ P1 برای خرابی جریان اصلی یا داده؛ P2 برای ناسازگاری قابل تکرار؛ P3 برای مورد محدودتر.

۲. ابتدا P0/P1 و سپس P2/P3 رفع می‌شوند. برای هر باگ، تست رفتاری یا بازتولید قبل/بعد، بررسی تفکیک حساب و نتیجهٔ ذخیره لازم است. تغییرهای هم‌پوشان بین عامل‌ها به‌صورت متوالی ادغام می‌شوند.

۳. در پایان، تست‌های مرتبط frontend/API، typecheck، build، سناریوهای مرورگری لازم و `git diff --check` اجرا می‌شود. محدودیت محیط/دادهٔ واقعی صریح ثبت می‌شود. گزارش یافته‌ها و سند جداگانهٔ پیشنهادهای محصول/معماری تحویل می‌شود.

## وضعیت اصلاح و راستی‌آزمایی

- A01 تا A27: اصلاح شده‌اند؛ Today اکنون کارهای برنامه‌ریزی‌شده برای روز/بازهٔ گذشته را در بخش «عقب‌افتاده» پس از کارهای امروز نشان می‌دهد. زمان محلی با بازگشت به صفحه، focus و عبور از نیمه‌شب تازه می‌شود.
- frontend کامل: ۲۴۰ فایل تست و ۲٬۰۲۱ تست پاس شدند. پس از آن یک تست رگرسیون دیگر برای صف قدیمیِ بدون مالک اضافه شد؛ فایل `offlineQueue.test.ts` پس از آن ۱۸ تست پاس‌شده دارد.
- API: ۳ فایل و ۴۳ تست پاس شدند؛ تست route حذف حساب به‌تنهایی نیز ۳ تست پاس‌شده دارد.
- `npm run typecheck` موفق؛ `npm run build` موفق؛ چهار فایل Python تغییرکرده با `ast.parse` بررسی شدند؛ `git diff --check` موفق بود.
- build هشدارهای موجود دربارهٔ chunkهای بزرگ و برخی dynamic/static importهای هم‌زمان را نشان می‌دهد، اما با موفقیت تمام می‌شود.
- تست end-to-end در Firebase/FastAPI واقعی اجرا نشده است. برای A01، Vercel به `ARSH_API_BASE_URL` و سرویس FastAPI deploy‌شده نیاز دارد؛ اپ native به `VITE_ACCOUNT_API_URL` نیاز دارد. بدون پیکربندی سرویس FastAPI endpoint عمداً خطا می‌دهد تا حذف ناقص موفق گزارش نشود.
- صف قدیمیِ محلی که مالک مشخصی ندارد، برای جلوگیری از پاک‌شدن دادهٔ حساب دیگری حفظ می‌شود؛ UI اکنون این پاک‌سازی محلی را ناقص اعلام می‌کند تا کاربر پیش از واگذاری دستگاه دادهٔ سایت را پاک کند.
